## 二、项目描述
### 2.1 项目背景
在当今社会，学习人工智能算法的需求显著提高，但人工智能算法复杂晦涩难懂，学习者难以入手。在学习中遇到疑问时，人工答疑存在资源分布不均、实时性差等缺陷。而泛用性AI（如deepseek），无法对专业知识与具体案例进行专业分析与归纳，且面对特定概念时，极易出现
“AI幻觉”（胡编乱造，脱离大纲）。
为了解决该学习问题，本项目将检索增强技术（RAG）与web技术相结合，基于学校网络环境，通过将论文、课本导入数据库，设计本款可控制回答边界、回溯说明提供步骤与源码、并对提供的错误代码进行分析/报错/修改/意见的“AI经典算法学习助教”系统，来辅助日常AI算法学习。

### 2.2项目名称
基于RAG技术的AI经典算法助教系统  
*(英文全称：RAG-powered Algorithm Assistant for Education 简称：RAG-AlgoTA)*

### 2.3项目概述
本系统是面向AI算法初学者的轻量化智能辅助系统。系统核心解决的问题在“算法论文高精度解析”与AI幻觉问题。

系统分为三个部分：

1. **vue3现代化多段适配前端**：提供用户交互界面（逐字打印 SSE 渲染、Markdown 及行内/行间 LaTeX 数学公式解析、PDF 随文预览），与管理员轻量级后台。
2. **FastAPI 高并发异步后端**：管理 JWT 多角色 RBAC 访问权限拦截、对话状态历史以及大模型 API 的调用分发。
3. **Celery 异步文档解析引擎**：执行 PDF 的物理段落抽取、PaddleOCR 图像识别兜底、层级父子分块（Hierarchical parent-child chunking）、高维向量入库及会话摘要离线压缩。

### 2.4 项目关联性

*   **与现有教学系统的关联**：系统可独立作为日常辅助教学站，亦可预留标准 RESTful 接口对接外部大模型与网站，实现模型升级。
*   **对现有客户网络环境的影响**：系统部署于云端服务器后，API 逻辑层需发起外网 HTTPS 请求与商业模型提供商通信，客户端通过 Web 浏览器访问系统。
*   **长期影响**：构建低成本AI算法数据库，积累用户高频疑惑日志，为讲解侧重点提供基础。

### 2.5 设计和实现上限值

*   **算力与计算资源限制**：系统完全舍弃对本地昂贵 GPU 硬件的依赖。无论是大模型的推理过程还是向量维度的嵌入（Embedding），全部基于服务器训练模型API接入，以保障系统能部署在 2核4G 内存的云主机中。
*   **开发周期限制**：项目需在10月完成从需求、设计到部署联调的全部生命周期。
*   **存储与 I/O 限制**：ChromaDB 本地持久化需确保云主机的磁盘空间和 I/O 读写稳定性，避免高并发读取同一向量文件导致文件锁死或 IO 等待过高。

### 2.6 假定条件和约束

**假定条件（用户基础）**：假定用户具备日常操作主流 Web 浏览器及 AI 对话工具的基础计算机水平；假定用户上传的 PDF 教材大部分为清晰的电子排版，少数公式密集区或扫描件有适当的 OCR 识别容错预期。

### 2.7 名词/术语解释

*   **RAG (Retrieval-Augmented Generation)**：检索增强生成。一种在给大模型提问前，先从本地库检索出相关内容，作为上下文一同喂给大模型以防幻觉的技术。
*   **SSE (Server-Sent Events)**：服务器发送事件。一种基于 HTTP 协议的单向流式推送技术，用于实现 AI 回复时逐字打印的打字机效果。
*   **ChromaDB**：轻量化向量数据库。
*   **SQLite FTS5**：轻量关系库的全文索引模块，用于关键词检索。
*   **RRF (Reciprocal Rank Fusion)**：倒数排名融合算法。

### 3.3 用户业务关系描述

1. **账号审批关系**：用户创建账号后，管理员审批账号通过，用户账号密码信息存入用户数据库。
2. **资料生命周期**： 管理员/用户上传资料->管理员审批并签名->后台更新当前版本并保存->后台离线解析->解析后成功写入数据库。
3. **对话审计关联**：用户对算法提问 -> 记录存入对话历史->系统保存相应单位出现次数。

### 3.4 系统面向用户群体

本系统受众是人工智能经典算法学习者，通常具备很高的移动端和电脑使用水平，追求即时响应和极简的类 ChatGPT 界面。他们期望 RAG 系统能够指出教材原文的具体页码，方便核验。

### 3.5 关键计算机资源

*   **云端部署资源**：要求宿主机支持标准 Docker 容器环境。MySQL 需要持久化挂载物理磁盘，由于向量库会写入高频数据，宿主机需预留 10GB 以上的存储空间。
*   **客户端资源**：用户仅需能接入互联网的常规电脑或智能手机，浏览器需支持现代 ES6 语法以及 Server-Sent Events 流解析接口。

## 四、功能性需求分析
### 4.1 用户当前工作模式与痛点分析
在引入本系统前，AI经典算法的学习过程如下：

* **工作流程**：学习者自学算法遇到困难->在网络搜索相关知识，阅读相关论文->无法系统归纳算法知识，学习效率低
* **核心痛点**：
  1. **过程繁琐**，搜索资料时间长，学习效率低；
  2. **缺乏归纳**，无法及时进行系统性总结；
  3. 直接询问通用大模型容易导致**AI幻觉**；
  4. 无法**迅速浏览**论文核心；

**当前模式与本系统对比**

### 4.2 构建该系统的目标
通过构建该系统，预计实现以下目标：
1. **管理目标**：规范知识层级化归档和鉴权，管理员轻松维护更新数据库与系统主prompt更新。
2. **使用目标**：实现 7×24h 毫秒级流式响应答疑，在 2核4G 低配机器上稳定支撑多班级日常并发提问。
3. **业绩目标**：

*   知识点检索定位时间从传统的几十分钟缩短至秒级；
*   通过双路检索配合 Prompt 强约束，将通用大模型在专业答疑中的“幻觉率”降低至 10% 以下。

* **要点：** 所有用户的密码存储时需要进行安全加密。
* **工作目标**：确保系统内不同角色的操作权限安全独立，提供无感知的身份验证，保护数据不越权泄露。

#### 4.4.2、论文解析与数据化管理
##### 业务描述
* **业务处理：** 管理员/用户上传通过的PDF资料，系统*   在后台自动对其执行文档解析与数据化处理。系统需提取其中的文本信息（包含对扫描图像进行文字识别），并按段落进行合理的切块存储，以构建答疑知识库。
* **要点：** 由于大文件解析过程耗时较长，系统必须采用后台静默解析任务，并在前端提供可视化的解析进度提示（如“待处理”、“解析中”、“已就绪”）。
* **目标：** 实现资料上传解析，最大化提取排版与公式信息，确保大部分的数据转化。

##### 用例及关键数据

*   **用例执行过程**：

    *   **管理**：选择本地 PDF 文件上传，设置资料名称。
    *   **系统后台**：接收文件，触发后台处理任务，轮询将状态标记为“就绪”或“失败”。

#### 4.4.3、 智能在线答疑对话
##### 业务描述

*   **业务处理情况**：用户通过自然语言输入专业问题。系统通过比对调取匹配度最高的几段资料原文，融合大模型的能力，以实时逐字打印的效果生成回答，并精准标明参考的内容所在的页码。
*   **要点**：必须通过设定约束词，限制 AI 仅能根据教材事实作答，不得编造数据库外非权威的答案；支持多轮对话上下文，并在后台自动提炼用户追问的实际含义（解决代词代指问题）。
*   **目标**：提供无延迟、无幻觉的 7×24 小时课后精准答疑，并能够对页码进行随文溯源。

##### 用例及关键数据

* **用例执行过程**：

  *   **用户**：新建会话并输入问题；在界面上浏览 AI 输出的回复，可以点击引用的源页码高亮对应的部分，并可继续在此会话中追加提问。

### 4.5 接口需求

#### 4.5.1 内部接口需求

系统内部各组件通过标准的 RESTful 协议或异步驱动进行交互：

*   **FastAPI 与 MySQL 之间**：采用 `SQLAlchemy` 进行异步驱动绑定（通过 `aiomysql` 连接池），利用 Pydantic 规范进行路由出入参的数据格式校验。
*   **FastAPI 与 Celery 之间**：通过 Redis 作为中间件（Broker & Backend）传递 JSON 格式的任务负载与状态结果。
*   **ChromaDB 读写接口**：后端服务内部通过 `chromadb.PersistentClient` 进程共享模式直接对宿主机本地数据库目录进行文件读写，保障读写一致性。

#### 4.5.2 模型服务与外部接口需求

系统采用**混合模型调用架构**，同时支持外部云端大模型 API 与本地私有化部署的大模型服务：

* **大模型服务接口（本地与外部混合部署）**：
  * **统一协议标准**：无论是本地服务还是外部 API，均遵循 OpenAI SDK 标准协议 标准，以便后端统一封装与灵活切换。
  * **外部云端大模型**：通过标准 HTTPS POST 协议调用，采用 Bearer Token（Authorization: Bearer <API_KEY>）进行鉴权。支持对话接口（/v1/chat/completions，支持 stream=True 流式响应）与文本向量化接口（/v1/embeddings）。
  * **本地私有大模型**：通过内网 HTTP/HTTPS 协议调用本地部署的推理引擎（如 vLLM / Ollama 等兼容 OpenAI API 规范的服务），支持与云端 API 相同的对话及向量化接口，不强制依赖外部鉴权。

* **图像识别 PaddleOCR 接口**：
  * 调用本地集成的 PaddleOCR Python 运行时接口进行高精度文字定位和字形解析。

 ## 五、 非功能性需求描述 (Non-Functional Requirements)

### 5.1 系统环境需求

*   **网络环境**：部署该系统的服务器须能够直接访问公网 HTTPS 端口（开放 80、443），以便与外部云端大模型服务器低延迟通信。
*   **客户端环境**：支持跨平台访问（PC 桌面端和移动端浏览器）。浏览器需完全兼容 HTML5 规范、SSE 协议流、以及 CSS3 自适应排版。
*   **并发特征**：在普通云主机配置下，能够支撑至多10 人同时进行高频 AI 检索答疑。

### 5.2 易用性和用户体验需求

*   **类打字机流式显示**：大模型输出响应必须在前端以逐字打印效果实时展示，首字响应时间（Time-to-First-Token）应限制在 1.5 秒以内。
*   **精准学术排版渲染**：针对理工科可能涉及的代码和复杂数学公式，系统必须支持 Markdown 格式与标准 LaTeX 排版（如利用 KaTeX 进行精准渲染）。
*   **清晰的解析状态反馈**：文件解析过程中，前端应显示相应的进度反馈（如“解析中”、“OCR识别中”、“向量化入库”），禁止界面长时间无响应。

### 5.3 软硬件技术需求

*   **开发技术选型**：前端采用 Vue 3 + TypeScript + Vite，后端采用 Python 3.11 + FastAPI。
*   **持久层软件**：关系型数据库 MySQL 8.0 负责高频交易事务，持久化 ChromaDB 作为向量索引，SQLite 作为全文倒排索引。
*   **服务器最低硬件配置**：
    *   物理资源：2核 CPU，4GB 内存，30GB SSD 磁盘存储空间（ChromaDB 向量及 PDF 文件存储需要）。
    *   部署形式：支持一键 Docker Compose 容器化部署（包含 FastAPI Web 镜像、Nginx 静态代理容器、MySQL 服务、Redis 消息队列以及 Celery Worker 解析进程）。

### 5.4 安全性需求

*   **JWT RBAC 身份校验**：用户凭证在登录时换取 JWT Token，默认有效期 8 天。敏感接口（如上传资料、流式对话、班级申请审批、配置修改）必须进行 JWT Token 认证，并校验角色权限，防止越权修改或窃取数据。
*   **防 SQL 注入与防 XSS 攻击**：
    *   使用 FastAPI 的 Pydantic 进行输入数据强类型校验，杜绝硬拼 SQL 语句，关系库交互完全采用 SQLAlchemy 参数化查询。
    *   前端对 AI 生成 of HTML 标签在渲染进 DOM 树前，必须进行 HTML 字符转义过滤（`markdown.js` 中需先对 `&`, `<`, `>` 符号进行正则替换），防范恶意 XSS 脚本执行。
*   **RAG 数据隔离**：
    *   向量数据库（ChromaDB）中，不同课程上传的教材必须在其 `metadata` 字典中注入 `course_id` 属性，并在底层向量检索 query 时强制应用 `metadata_filter` 进行隔离过滤，杜绝跨课程知识越权获取。
    *   物理 PDF 课件保存在服务器本地受保护的文件目录（如 `./uploads/textbooks/`）或对象存储中，前端仅提供分段片段展示及出处页码定位，不向学生角色提供原始大文件下载接口。

### 5.5 可维护性需求

*   **分层配置系统**：系统采用“三层优先级覆盖”机制，即 `config_override.json`（管理员后台运行时修改） 覆盖 `.env`（宿主机敏感密钥环境变量），覆盖 `config.yaml`（非敏感的默认大模型、检索 Top K 等参数配置），覆盖代码默认值。方便运维人员无需重启容器即可动态调整系统参数。
*   **日志记录与追踪**：系统产生的各类异常错误信息由 `core/exceptions.py` 全局异常处理器统一捕获，记录为 standard log 文件，屏蔽底层的数据库物理表结构暴露出站，保障系统日志安全。
